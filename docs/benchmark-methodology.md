# Benchmark methodology

These checks exercise the real SQLite memory engine and MCP stdio transport with
generated data. They measure a bounded workload on one machine; they are not a
promise of performance on other machines or a measure of an AI model's memory
usefulness.

## Reproduce the workload

From the repository root, use the installed development virtual environment.
See [Contributing](../CONTRIBUTING.md) to create it on a fresh checkout:

```sh
.venv/bin/python scripts/benchmark_memory.py \
  --output verification/benchmark/my-run \
  --records 10000 --seed 20261009 \
  --recalls 240 --mcp-recalls 200 \
  --workers 4 --concurrent-operations 1000
```

Choose a new output directory for each run. The script refuses to reuse an
existing benchmark database or metrics file. `--generate-only` writes the
fixture plan without opening a database. Smaller `--records` values reduce
runtime but must fit all labelled fixtures; the parser reports the minimum.

The default corpus is loaded through 10,000 public `remember` calls. The same
nested dataset is measured at 100, 1,000, 5,000, and 10,000 records. Each
checkpoint runs the same 20 query arguments once for warm-up, then cycles them
for 240 timed recalls. The MCP phase performs 20 warm-up and 200 timed recalls.
Raw samples, scale summaries, corpus records, and check results are retained
beside the report.

Evaluate the frozen query suite against the preserved baseline snapshot:

```sh
PYTHONPATH=src .venv/bin/python scripts/evaluate_recall.py \
  --database verification/benchmark/my-run/data/corpus_snapshot.db \
  --manifest verification/benchmark/my-run/fixture_manifest.json \
  --queries scripts/recall_queries.json \
  --output-dir verification/benchmark/my-run
```

The committed suite contains 80 authored queries against 44 distinct target
facts, plus 29 context/lifecycle checks and nine diagnostic queries. The suite
was frozen before its results were observed. Its full query text and target
keys are available for inspection; multiple queries reuse the same facts, so
observations are correlated and no accuracy confidence interval is claimed.

`metrics.json` and `latency.csv` hold performance results; `quality.json` and
`query_results.csv` hold target-retrieval results and failure details. The
scripts return a nonzero exit code for failed correctness checks. Missing a
target on a paraphrase is a recorded retrieval outcome rather than an engine
error.

## Data and isolation

All records are synthetic. Each run supplies an explicit database path under an
isolated run directory; it must never use the default personal memory database.
The corpus uses a fixed random seed and includes repeated technical vocabulary,
different scopes and projects, and distractors. A seed makes the generated
content reproducible. Record IDs and timestamps are generated by the service,
so equal-score ordering can vary between runs.

The baseline `data/corpus_snapshot.db` preserves the original generated corpus
for retrieval evaluation. The main `data/memory.db` later receives additional
concurrency records; its final count is reported separately. The default
10,000-record run adds 1,200 unique worker observations and one shared record,
ending at 11,201 rows. Corpus JSONL retains submitted content, while the engine
applies its ordinary normalization, including trimming surrounding whitespace.

## Timing

Engine timings include the public `MemoryStore` operation: validation, opening
its SQLite connection, locking, query or transaction, and closing the
connection. They do not include an MCP client, server startup, network calls, or
AI generation. Each write is a normal committed public operation rather than a
bulk SQL import.

Warm measurements follow corpus insertion and declared warm-up queries. New
SQLite connections do not imply a cold operating-system disk cache. Fresh MCP
process measurements include process launch and protocol initialization; they
also may benefit from the operating system's cache. No cache flushing is
performed.

Throughput is completed operations divided by wall-clock seconds for its
declared workload. Concurrent operation latencies include contention; aggregate
throughput uses the shared workload duration rather than the sum of individual
latencies. Startup and ingestion are reported separately from steady-state
recall.

Concurrent attempted and successful throughput are reported separately. The
ingestion rate is **new records per second** for each segment; the first segment
also includes two explicit supersession updates in its elapsed time. The legacy
`write_ops_per_second` JSON field has this same records-per-second meaning. The
single MCP startup observation is not a startup latency distribution.

Latency p50, p95, and p99 use the nearest-rank definition: sort the samples and
select the one-based rank `ceil(N * percentile / 100)`. They are observed sample
quantiles, with no confidence interval. At the default 240 samples per scale,
p99 is the third-highest sample; it does not estimate rare worst-case latency.
The fixed query mix makes scales comparable, but aggregate latency depends on
that mix and is not a promise for every query.

The multiprocess workload cycles through 30 new inserts, 40 recalls, 15 list
operations, 10 updates, four shared duplicate attempts, and one integrity status
operation per 100 requests per worker. At the default settings, four workers
issue 4,000 timed requests. Status includes integrity checks and can be much
slower than a recall. Process startup and shutdown are included in aggregate
concurrent wall time. This workload measures contention among local processes;
it is not a network load test.

The robustness phase verifies explicit history, expiration and project
filters, then backs up the isolated database and restores it to another
isolated path. Restore verification compares every durable row and a search
result. The MCP crash check sends `SIGKILL` only to its own benchmark server
after an acknowledged commit, restarts the server, and checks the saved record.
It does not simulate power loss or a crash midway through a transaction.

## Charts and offline report

Plotting dependencies are optional and can use a separate environment. The
pinned [plotting requirements](../requirements-benchmark.txt) were installed
and validated on Python 3.10 for this run. They are separate from the server's
runtime dependencies. To regenerate the figures and HTML report:

```sh
python3 -m venv .bench-venv
.bench-venv/bin/python -m pip install -r requirements-benchmark.txt
.bench-venv/bin/python scripts/plot_benchmark.py \
  --input verification/benchmark/my-run
```

The `charts` subdirectory contains PNG and SVG figures plus a standalone HTML
report with query filters. The recall distribution figure pools the engine
observations across all measured scales; the scale figure shows each checkpoint
separately. Concurrent workers choose queries randomly from the same 20-query
pool while performing the mixed workload. These distributions do not isolate
transport overhead. The HTML file embeds its charts and query rows and needs
no external service to display or filter them.

## Memory measurements

On this execution host, Python's `resource.ru_maxrss` carries a high-water value
inherited from its launcher: a fresh small Python process reported 543,432 KiB
there while its own `/proc/self/status` high-water value was about 10 MiB. The
retained historical counter therefore cannot establish this service's memory
footprint. Read Linux `VmRSS` and `VmHWM` for the measured process instead. Their
`kB` values use 1,024-byte units; divide by 1,024 for MiB. Process RSS is not
whole-system memory use, and separate process RSS values may include shared
pages.

Reproduce the server profile separately:

```sh
.venv/bin/python scripts/profile_memory.py \
  --database verification/benchmark/my-run/data/corpus_snapshot.db \
  --output verification/benchmark/my-run/memory_profile.json --recalls 200
```

This starts a new MCP server and reads its own child process's `/proc` memory
fields at initialization, after 20 warm-up and 200 further recalls, and after an
integrity check. These extra calls are excluded from the main benchmark's timed
operation totals. Sampled RSS can miss brief peaks; `VmHWM` records the process's
high-water value.

## Retrieval evaluation

Query cases have designated target records chosen before retrieval. Target
hit@1 and hit@5 measure whether the target appears in the first result or the
first five results. MRR@5 is the mean reciprocal rank of that target within the
first five results, using zero for a miss. These are target-retrieval metrics:
they do not label every returned record as relevant or irrelevant, and they
cannot establish precision, exhaustive recall, or general search accuracy.

The evaluation separates literal keywords, phrases, prefixes, contextual
filters, and paraphrases. Unique-token lookups are useful correctness and
latency probes, but they are easier than recalling a fact from an independently
worded question. Shared-word paraphrases and paraphrases with little or no
indexed-word overlap must be reported separately.

The current engine uses safe keyword expressions. It tries an AND query first
and returns those matches if there are any, then falls back to OR only if there
are none. The index includes content, category, and project. An OR fallback can
return unrelated memories that share common words; synonym understanding is
not implemented.

Project isolation, expiration, supersession, update/delete index synchronization,
and duplicate suppression are correctness invariants. They are checked
separately from target-ranking scores. Recorded retrieval errors count as
misses and make the evaluator exit nonzero; errors that prevent reporting abort
the run. Failed checks must not be interpreted as a passing benchmark.

## Interpreting results

The corpus and relevance targets are authored fixtures, not a sample of real
user histories or independent human relevance judgments. The results establish
behavior for the disclosed workload only. Storage, CPU load, cache state,
Python/SQLite versions, corpus length, and query selectivity can change timings.
Repeated local runs help detect regressions, but cannot establish capacity for
an unspecified deployment.
